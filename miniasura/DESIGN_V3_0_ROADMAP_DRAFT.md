## §0 必须先纠正的四个路线错误

### R1 期数撞车（致命）

原提案把「宝石 + 套装 + 属性点」编号为 V2.9-B，但 V2.9-B 已经被「爬塔战报 + 稀有 fled」占用并冻结入仓，且 B1/B2 均已实施。原提案的 `smoke_v29b` 也与现有 `tests/smoke_v29b.py` 冲突。

**修订**：宝石/套装/属性点整体后移至 V3.0-A，不在 V2.9-B/C/D 插队。

### R2 区域图与「不重写引擎」自相矛盾

原提案原则 9 写「旧系统不推倒重来」，但 §2.2 的 graph 若要替换 `engine.run_game()` 的线性主循环，就是重写主循环；`maps.txt` 也要加入通路语义。

**修订**：采用**分层区域导航**，不是把主线改成 graph：

- 主线 10 图仍是线性资产，`engine.run_game()` 主循环不被 graph 替换。
- 新增 `world.py` 只负责生活地点、重访入口、解锁状态、区域间导航。
- 主线地点由现有周目/图进度解锁；生活地点由 world 层解锁。
- graph 只描述生活地点与主线入口之间的关系，不接管战斗结算、任务推进、周目逻辑。

### R3 「结构化数据全部进 game.ini」不成立

ini 适合扁平调参，不适合节点+边、NPC 名册、套装件、调查线索、收集品表。硬塞 ini 会让校验器变成字符串解析器。

**修订**：

- `game.ini` 只放扁平数值：倍率、价格、概率、上限、每级点数、时辰消耗。
- 结构化数据走**新增外部文本表**（不直接改 mpak），例如：
  - `data/gems.txt`、`data/sets.txt`
  - `data/world.txt`（节点/边/解锁条件）
  - `data/npc.txt`
  - `data/dialogue_ext.txt`、`data/achievements_ext.txt`
- 每个新模块自带 `check_*()`，由 `validate.py` 汇总；新增数据未过校验即红。

### R4 门禁不能缩水

原提案 §7 说 B/C/D「只做本期 + 上一期回归，不做全链」。这会允许跨期破坏潜伏数期，违背 V2.9-A 以来「全链全绿才出期」的纪律。

**修订**：每期必须跑 `v20→当前期` 全链。可以优化测试执行时间，但不得删除覆盖。无 GUI 环境仍须显式安装 PySide6 后再跑。

## §3 V3.0 各期技术落点

### V3.0-A：宝石 + 套装 + 属性点

- 新模块建议：`gem.py`、`sets.py`、`attrs.py`，每个 ≤150 行；超额必须先拆模块，不靠塞 engine。
- 数据：数值进 `game.ini`；宝石种类/套装件/属性点规则进 `data/*.txt`。
- schema 12 只新增真实使用字段：`gems`、`set_pieces`、`attr_points`。禁止“预留字段”。
- 平衡原则：玩家变强可以，怪物数值不自动跟着变；CLI 全通基线必须显式重钉，并在提交信息写明新旧值与原因。
- 强化 / 宝石 / 套装三层必须分别断言：单层生效、两两组合不重复计、三层上限独立且可解释。

### V3.0-B：叙事 + 世界壳

- 叙事只做 GUI 逐行；CLI 默认一次倾倒，保证原 CLI 输入模型不位移。
- 分支写 `choices`，只影响对话、小奖励和后续重访文案；本期不做多结局。
- 世界壳是 `world.py` 导航层：生活地点、解锁、重访、商店日程；不得替换 `engine.run_game()` 的 10 图线性推进。
- 时间先做 5 档；天气先影响世界/商店/遭遇入口。若要影响命中/伤害公式，必须单独设计战斗上下文并同步修订 Lua 与 combat 行数；默认推迟到 V3.1。

### V3.0-C：主城生活 + 副本补充

- 打工 = 花时间换金币/材料，不做打工小游戏。
- 小游戏只保留猜拳、钓鱼两个“按一次键”的轻量交互。
- 收集品不给战力，只进图鉴/称号线索。
- 副本评分只使用 V2.9-A 已有战报字段：rounds/taken/misses；不新增战斗埋点。
- Boss 重访收益打折，首杀奖励不得重复发放。

### V3.1：开放世界全量

- 声望只做 5 势力 × 3 档；不掉声望，惩罚最多影响价格/入口，不废档。
- 同伴只保留“每场自动作用一次”的低耦合模型；老猴与第 2 同伴互斥上场。
- 通关后生活是继续玩已有系统，不是隐藏结局或多结局。

## §5 门禁与基线纪律

1. 每期新门禁文件按实际期号命名：`smoke_v29c.py`、`smoke_v29d.py`、`smoke_v30a.py`……禁止复用旧号。
2. 每期出口 = 本期专项门禁全绿 + `v20→当前期` 全链绿 + `validate` 全绿 + CLI 全通基线显式核对。
3. 玩家侧数值变化会导致基线变化时：允许重钉，但必须给出旧值 → 新值 → 原因 → 复核人可复现命令。
4. 不允许通过“怪物跟着玩家变强”掩盖测试失败；怪物侧调参必须独立成批、独立说明。
5. GUI 新增逐行/时间/天气不得把 CLI 全通变成强交互流程；CLI 默认保留速通模式。
6. 所有随机内容（天气、集市刷新、扭蛋）测试必须注入确定性种子；禁止靠概率碰运气。

## §8 路线结论

原开放世界提案的**方向可用**，但原稿的期数、数据落点和门禁策略不能直接施工。修订后路线为：

```text
V2.9-B（已完成）→ V2.9-C GUI战报 → V2.9-D1 称号/成就/幻影榜
→ V2.9-D2 日常/周常/签到 → V3.0-A 宝石/套装/属性点
→ V3.0-B 叙事/世界壳 → V3.0-C 主城生活/副本补充 → V3.1 开放世界全量
```

本文不构成任何一期实施授权。下一步应先审路线；确认后，下一期仍须单独出细案冻结稿，再由业主一句话开工。
